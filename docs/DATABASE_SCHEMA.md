# UtsavAI — Database Schema and Data Model

**Version:** 1.0  
**Date:** 31 October 2026  
**Database:** Supabase-managed PostgreSQL

## 1. Database conventions

- Primary keys: UUID, generated by the database.
- Timestamps: `timestamptz`, stored in UTC; display in the event's IANA time zone.
- Monetary values: `numeric(12,2)` plus ISO 4217 `char(3)` currency. Never use floating-point for persisted money.
- Soft deletion: use `archived_at` or explicit status where recovery/audit matters; use hard deletion only for defined privacy deletion workflows.
- Every event-owned table includes `event_id` directly or through a parent relation and is protected by event membership authorization.
- Foreign keys use explicit `ON DELETE` behavior. Event-owned children generally cascade when an event is permanently deleted; audit/legal retention policy may require anonymization or delayed deletion instead.
- IDs exposed in URLs are not authorization. Every request still checks permission.
- `created_at` and `updated_at` are database-maintained where practical.
- JSONB is reserved for versioned, flexible preferences or AI artefacts; normalized columns remain the source of truth for operational data.

## 2. Relationship overview

```text
auth.users 1──1 profiles
profiles 1──N events (owner)
events 1──N event_members ──N profiles
events 1──1 event_preferences
events 1──N event_functions
events 1──1 budgets 1──N budget_categories
budgets 1──N expenses
events 1──N tasks 1──N task_dependencies
events 1──N event_vendors 1──N vendor_quotes
events 1──1 gift_registries 1──N gift_items
  gift_items 1──N gift_reservations
  gift_items 1──N gift_contributions
events 1──N ai_conversations 1──N ai_messages
events 1──N change_proposals
events 1──N audit_logs
```

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `event_id` | uuid | FK → events.id ON DELETE CASCADE |
| `budget_category_id` | uuid | FK → budget_categories.id; category must belong to same event budget |
| `vendor_id` | uuid | Nullable FK → event_vendors.id |

**Budget semantics:** `total_limit` is the host's ceiling. `planned_amount` is the planned category allocation. Expense totals are actual records by status. Do not silently force allocations to equal the budget ceiling. Warnings are application-calculated; overruns must be representable.

### 7.3 `gift_reservations`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `gift_item_id` | uuid | FK → gift_items.id ON DELETE CASCADE |
| `guest_alias` | varchar(80) | Nullable; optional public display alias |
| `status` | text | `reserved`, `cancelled`, `fulfilled`, `expired` |
| `cancellation_token_hash` | bytea/text | Nullable unique hash if cancellation link is enabled |
| `expires_at` | timestamptz | Nullable; if enabled, backend treats expired reservations as inactive |
| `idempotency_key` | varchar(100) | Required for public create action; unique in scope |
| `created_at`, `updated_at` | timestamptz | Required |

Partial unique index on `gift_item_id` WHERE status = `reserved` and (where practical) expiration has not passed. Since PostgreSQL partial indexes cannot use volatile `now()` predicates, maintain active/expired status transactionally during reservation attempts or use an `expires_at`-aware lock-and-update routine. Index `(gift_item_id, status)`.

### 7.4 `gift_contributions`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `gift_item_id` | uuid | FK → gift_items.id ON DELETE CASCADE |
| `guest_alias` | varchar(80) | Nullable |
| `amount` | numeric(12,2) | CHECK > 0 |
| `currency` | char(3) | Must match event/gift currency |
| `status` | text | `pledged`, `verified`, `withdrawn`, `refunded` |
| `verification_method` | text | Nullable; `host_manual_confirmation` or `payment_provider_webhook` |
| `verified_at` | timestamptz | Nullable |
| `verified_by` | uuid | Nullable FK → profiles.user_id |
| `provider_reference` | text | Nullable; reserved for future verified provider event |
| `idempotency_key` | varchar(100) | Required for public create action |
| `created_at`, `updated_at` | timestamptz | Required |

Constraints:
- `amount > 0`.
- `status='pledged'` requires no `verified_at`, `verified_by` or verification method.
- `status='verified'` requires `verified_at` and `verification_method`.
- `host_manual_confirmation` requires `verified_by` and must be labelled **host-confirmed**, not provider-verified.
- `payment_provider_webhook` requires a provider reference and signature-verified webhook audit record; this method is future-only in MVP.
- `withdrawn` and `refunded` are not counted toward active pledged/confirmed target totals according to explicit aggregate rules.

Group target cap cannot be enforced with a row-level CHECK. Use a transaction/row lock or a single database function to calculate active total and insert the new pledge atomically. Add index `(gift_item_id, status)` and unique idempotency scope.

**Important semantics:** `pledged` means guest intent only. `verified` is a workflow status with a provenance method. In MVP only a host's manual confirmation is possible; UI wording must say host-confirmed/received offline and never payment-provider verified. UtsavAI does not collect or hold money in this release.

## 9. Audit and idempotency

### 9.1 `audit_logs`

Append-only records containing `id`, `event_id`, nullable `actor_user_id`, `actor_type` (`user`, `public_guest`, `system`), `action`, `entity_type`, `entity_id`, safe `metadata` JSONB, `request_id` and `created_at`.

- No raw tokens, API keys, payment credentials or full guest contact details in metadata.
- Restrict update/delete privileges; only a tightly controlled retention workflow may purge logs.
- Index `(event_id, created_at DESC)` and `(entity_type, entity_id)`.

### 9.2 Idempotency

Use an `idempotency_records` table or operation-scoped unique keys for public gift actions and mutation endpoints. Suggested fields: `scope_key`, `idempotency_key`, `request_hash`, `response_reference`, `created_at`, `expires_at`. Enforce a unique `(scope_key, idempotency_key)` constraint. For the per-row gift tables, enforce uniqueness on `(gift_item_id, idempotency_key)`. Reusing a key with a different request hash returns 409.

## 10. Authorization and RLS policy map

- Enable RLS on every application table exposed through a database API. The FastAPI runtime role is `NOBYPASSRLS`; it is not a superuser.
- For authenticated event tables, policies require the transaction-local `app.user_id` to be an active member of the row's event and the role to permit the operation.
- Profile rows are readable/updatable only by their owner, with narrowly scoped fields.
- Event owner is canonical; `event_members` is used for membership/roles. Ensure membership policies do not recurse.
- Public guest routes do not grant general anonymous table access. FastAPI hashes the supplied token and sets a transaction-local candidate-token-hash context. RLS permits the initial lookup only when it exactly matches an active registry's stored hash; after that, the backend sets a registry-ID context. Public policies and service methods return allow-listed fields for that registry alone.
- If a security-definer function is introduced for a narrowly scoped capability, it must live in a non-exposed schema, pin an empty `search_path`, fully qualify objects, have minimal owner privileges and have explicit `EXECUTE` grants. Prefer ordinary invoker logic where possible.
- RLS is not a substitute for service-layer authorization; both must be tested.

## 11. Data integrity requirements

1. Every child record belongs to the same event as its parent and any referenced function/vendor/member.
2. Budget, vendor quote, gift target and contribution currency match the event currency in the MVP.
3. Dates are valid in event time zone and `end_at >= start_at`.
4. Task dependencies cannot self-reference, cross events or create cycles.
5. Only one active individual-gift reservation exists at a time.
6. Active group-gift pledges plus verified amounts cannot exceed the target under concurrent writes.
7. Contribution status and verification metadata remain internally consistent.
8. Event revision increments for every material mutation represented in shared planning context; AI chat/read operations do not increment it.
9. Public registry tokens are stored as hashes and can be revoked/rotated.
10. Domain updates and corresponding audit records commit in the same transaction where practical.

## 12. Migration and seed policy

- Use ordered, immutable SQL migration files.
- Never edit a migration already applied to a shared environment; add a corrective migration.
- Include constraints, indexes, grants, RLS policies and policy tests alongside schema creation.
- Keep demo/sample data in a separate seed script and clearly identify it as synthetic.
- Production and demo environments must use separate Supabase projects or isolated databases; demo reset must never target production.
- Add database-level tests for allowed and denied operations, concurrency routines and cross-event reference rejection.

## 13. Future extensibility

- Event categories are string/configuration values with category templates, not schema-level enums.
- `event_functions` and generic tasks support multi-function weddings and single-session events.
- New preference fields use versioned JSONB only when flexible; high-use/searchable values should become normalized columns.
- Payment references are reserved but no payment-provider data is considered active until a provider is selected and webhook verification is implemented.
- A future `vendor_profiles` global directory can be added without changing event-scoped `event_vendors` records; the latter may reference a profile ID later.

## Phase 1 Implementation Notes

Recorded when Phase 1 was implemented. Where the implementation differs from or adds to the text
above, the migrations in `supabase/migrations/` are authoritative.

1. **Tables delivered:** `profiles`, `events`, `event_members`, `audit_logs`. No tables for later modules.
2. **`events.event_type`** is `varchar(40)` with a format check, not an enum. Enabled categories are
   application configuration (`app/core/domain.py`), currently only `wedding`.
3. **Lifecycle:** `draft`, `planning`, `completed`, `archived`. `draft -> planning`,
   `planning -> draft | completed`, `completed -> planning`. `archived` is reached only through
   `DELETE /events/{id}`, is owner-only, terminal in Phase 1 and read-only.
4. **Revision:** maintained by the `events_before_update` trigger; the runtime role cannot write it.
5. **Owner invariant:** a deferred constraint trigger rejects any event without an active owner
   membership at commit. The API creates event and membership in one transaction.
6. **RLS without recursion or definer functions:** `event_members` SELECT is limited to the caller's own
   rows. Listing all members of an event is deferred to the collaboration phase and will be added with a
   dedicated, reviewed mechanism.
7. **Grants:** the runtime role `utsavai_app` has column-level INSERT/UPDATE grants, no DELETE or
   TRUNCATE anywhere, and `audit_logs` is append-only. `anon` and `authenticated` are revoked.
8. **Profile provisioning** is lazy, from the verified JWT subject, not by a trigger on `auth.users`.
9. **Not yet implemented from this document:** `idempotency_records` and every later-phase table.
