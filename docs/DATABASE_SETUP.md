# Database Setup

## Migrations

All schema changes are version-controlled SQL in `supabase/migrations/`, applied in filename order.
Nothing is created at application startup.

| Migration | Contents |
| --- | --- |
| `20261101000100_foundation` | `app` schema, `utsavai_app` runtime role (NOBYPASSRLS), `app.current_user_id()`, timestamp and timezone trigger helpers |
| `20261101000200_profiles` | `profiles` (PK references `auth.users.id`) |
| `20261101000300_events` | `events` with all constraints, indexes, revision and archive trigger |
| `20261101000400_event_members` | `event_members`, one-active-owner index, deferred owner-membership constraint trigger |
| `20261101000500_audit_logs` | append-only `audit_logs` |
| `20261101000600_rls_and_grants` | RLS enablement, policies, least-privilege grants, Data API revokes |

### Key guarantees (all covered by tests)

* UUID primary keys generated by the database; `timestamptz` throughout; no floating point.
* `events.event_type` is a validated string, never a PostgreSQL enum.
* `revision` starts at 1 and is incremented by a trigger. The runtime role has no UPDATE privilege
  on `revision`, `owner_user_id`, `archived_at` or `event_type`.
* An event cannot commit without an active owner membership (deferred constraint trigger).
  The application creates both rows in one transaction.
* Archiving is a soft state change. Archived rows are read-only. The runtime role has no DELETE.
* IANA timezone names are validated in the database.

## Local database

```bash
ADMIN_URL=postgresql://postgres:<pw>@localhost:5432/postgres scripts/setup_local_db.sh utsavai_test
```

Local-only stand-ins for `anon`, `authenticated`, `service_role` and `auth.users` come from
`supabase/tests/bootstrap_local.sql`. The real migrations run unchanged.

## Supabase project

1. Create a Supabase project (use a separate project for development, test and production).
2. Apply migrations. Either:
   * Supabase CLI: `supabase link --project-ref <ref>` then `supabase db push`, or
   * SQL editor: paste each migration file in order.
3. Give the runtime role a password and the ability to log in (run once, as the project owner):

   ```sql
   alter role utsavai_app with login password '<generate-a-long-random-password>';
   ```

   Store the password only in your secret manager and deployment environment.
4. Build the connection string. Through the Supabase pooler the user is `utsavai_app.<project-ref>`:

   ```text
   postgresql://utsavai_app.<ref>:<password>@<pooler-host>:6543/postgres?sslmode=require
   ```

   Port 6543 is transaction mode, port 5432 on the pooler is session mode, and the direct
   connection also works. The design is safe in all three (see below).
5. Verify the identity-context design on your project (this is the live gate P1-14):

   ```bash
   cd apps/api
   DATABASE_URL='<runtime connection string>' SUPABASE_URL=https://<ref>.supabase.co \
     uv run python ../../scripts/verify_supabase_live.py
   ```

   The script creates no data. Exit code 0 means every check passed.

## Row-level security design

Every request runs in one transaction. FastAPI executes
`select set_config('app.user_id', <verified uuid>, true)` first. The third argument (`true`) makes
the value transaction-local, so PostgreSQL discards it at COMMIT or ROLLBACK. This is what makes
the design correct under the transaction-mode pooler, where consecutive transactions on one
server connection can belong to different users. Policies read it through
`app.current_user_id()`, which returns NULL when unset, so everything is denied by default.

| Table | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| `profiles` | own row | own row | own row (display name, locale, timezone) | none |
| `events` | owner or active member | `owner_user_id` = caller | owner or active editor (limited columns) | none |
| `event_members` | own rows | caller as owner of own event | none | none |
| `audit_logs` | active owners of the event | caller as actor on a visible event | none | none |

Design choices worth knowing:

* No `SECURITY DEFINER` functions. `event_members` is readable only for the caller's own rows, which
  keeps policies free of recursion. Listing other members of an event arrives with the
  collaboration feature using a dedicated mechanism.
* The `anon` and `authenticated` roles used by the Supabase Data API are explicitly revoked from
  these tables. The browser has no direct database path.
* Defence in depth: the connection pool resets all session settings when a connection is
  returned, and the backend refuses to start if its role is a superuser or has BYPASSRLS.

## Resetting a local database

`scripts/setup_local_db.sh <name>` drops and recreates the named local database. It refuses
Supabase hostnames.

## Adding a migration

Create `supabase/migrations/<UTC timestamp>_<name>.sql`. Never edit an applied migration. CI applies
all migrations to two fresh databases and fails if the resulting schemas differ, if a table lacks
RLS, or if `BYPASSRLS` / `SECURITY DEFINER` appear.
